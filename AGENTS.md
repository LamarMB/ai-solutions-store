# AGENTS.md — правила проекта

Этот файл — главный источник правил для людей и ИИ-агентов, работающих с репозиторием.
Статус этапов — в [docs/roadmap.md](docs/roadmap.md), запуск — в [README.md](README.md).

## Цель

Сайт компании по внедрению ИИ и автоматизации для бизнеса разных отраслей в формате
интернет-магазина цифровых решений: каталог, категории, отрасли, поиск, карточки решений
(стоимость, этапы внедрения, требования к данным и доступам заказчика, состав работ,
ограничения), ИИ-консультант по услугам, заявка на выбранное решение.
Позже: CRM, агенты поиска клиентов, автоматизация продаж, возможно онлайн-оплата.

## Согласованная архитектура (не пересматривать без причины)

- Одно приложение: Next.js 16.x (App Router) + TypeScript + Tailwind CSS, пакетный менеджер npm.
- Node.js 24 LTS (`.nvmrc`, `engines`). Основная среда разработки — Windows.
- Каталог — файлы в репозитории со строгой схемой (Zod). Категории и отрасли —
  независимые классификации.
- Цена хранится структурно: тип (фикс / «от» / по запросу), сумма в минимальных
  единицах валюты, валюта.
- Заявка — черновик заказа из позиций «решение + пакет», чтобы позже добавить корзину
  и оплату без переписывания.
- ИИ-консультант — через интерфейс сменного провайдера (`ChatProvider`) с mock-реализацией.
  Конкретный LLM-провайдер не выбирается без проверки доступности и стоимости.
- Импорты внутри `src/` — через алиас `@/*` (`tsconfig.json` → `./src/*`).

## Жёсткие правила

- Работаем небольшими этапами. После каждого этапа — проверка и подтверждение владельца.
- Демонстрационные данные явно помечаются (`isDemo` + видимая плашка «Демо»).
- Не выдумывать реальные кейсы, отзывы, гарантии и результаты от имени компании.
- Не подключать реальные платежи, не собирать реальные персональные данные,
  не разворачивать в production (только по отдельному решению).
- Отделять проверенные факты от предположений; не придумывать результаты проверок.
- Секреты не коммитятся. Пример переменных — `.env.example`, реальные — `.env.local`.
- Не добавлять зависимости без необходимости.

## Специализация: медицинские клиники

- Сайт посвящён автоматизации частных медицинских клиник. Публично — только
  `clinic-ai-administrator`, `patient-request-routing` (концепция) и
  `patient-ai-assistant` (концепция).
- Первый канал ИИ-администратора — сообщения сообщества ВКонтакте. Чат на сайте и другие
  каналы не обещаются, пока не подключены. Интеграция с МИС оценивается отдельно;
  прототип использует тестовое расписание с вымышленными врачами и пациентами.
- Остальные решения помечены `hidden: true`: файлы сохраняются, но не попадают в каталог,
  консультант, sitemap и навигацию. Публичный слой — `getSolutions()`, `getCategories()`,
  `getIndustries()`; все записи — `getAllSolutions()` (только для проверок данных).
- Тарифы: `price` — внедрение, `monthlyPrice` — обслуживание в месяц, один пакет может быть
  `recommended`; `pricingNote` — пометка «цены предварительные». Цены выводятся через
  `PackagePrice` / `formatPackagePrice`.
- Сбор заявки и подтверждённая запись — разные вещи: подтверждённую запись обещаем только
  при работающей интеграции с расписанием клиники.
- ИИ не ставит диагнозы и не назначает лечение; консультант отказывает в медицинских
  советах. Медицинские документы и жалобы — специальная категория персональных данных:
  не собираются и не хранятся до правовой оценки и подготовки инфраструктуры.
- Сценарий пациента на главной (`src/content/patient-journey.ts`) — описание будущей
  функциональности, без имитации записи или передачи данных.

## VK-бот (прототип)

- План и статус — `docs/vk-bot-plan.md`; код — `src/bot/`, симулятор — `npm run bot:sim`.
- Бизнес-логика не знает о ВКонтакте и LLM: канал вызывает `createBot(...).handle()`,
  разговор ведёт `src/bot/conversation/orchestrator.ts`, LLM подключается как
  `ConversationModel`, МИС — как `ScheduleProvider`. Подробности —
  `docs/conversational-bot-deploy.md`.
- Только вымышленная клиника и данные. Бот не собирает документы, анализы, фото, ФИО и
  телефоны. Для маршрутизации хранится минимум: краткая жалоба, ответы на уточнения
  (травма, длительность, тревожные признаки), последние 12 реплик без контактов — в
  SQLite, не дольше `BOT_HISTORY_HOURS` (24 ч) и до команды «сброс». В журнал — никогда.
- Бот — административная маршрутизация, не диагностика: без диагнозов, лекарств,
  лечения и успокоения («ничего страшного»). Тревожные признаки проверяет
  `src/bot/conversation/safety.ts` (правила с учётом отрицаний) до модели; модель может
  повысить срочность, но не отменить правило. При экстренных признаках — сразу 103/112,
  без расспросов и записи. Ответы модели с лекарствами, диагнозами, временем и ценами
  отбрасываются (`isUnsafeReply`); время и цены показывает программа из справочника.
- Записи — SQLite (`node:sqlite`, файл `.data/bot.sqlite` вне Git). Двойное бронирование
  исключено уникальным индексом по активному слоту; подтверждение и отмена — только из
  сохранённого состояния, не из данных кнопки.
- Кнопки укладываются в ограничения ВКонтакте (проверяется тестом): до 10 кнопок и 6 рядов,
  подпись до 40 символов, payload до 255 символов — сверить с dev.vk.com.
- Канал ВКонтакте — `src/bot/vk/`: только **Bots Long Poll** (Callback API не используется),
  запуск `npm run bot:vk`, проверка настроек `npm run bot:check`, инструкция —
  `docs/vk-bot-run.md`. Бот отвечает только `VK_ALLOWED_USER_IDS`; повторные события
  отбрасываются по таблице `processed_events`, `random_id` детерминирован.
- LLM — `OpenAiConversationModel` (`src/bot/llm/`, Responses API через `fetch`, без SDK,
  Structured Outputs). Модель возвращает действие из `MODEL_ACTIONS` и короткий ответ;
  решение проверяется `sanitizeDecision` (id врачей, даты, текст). Подтверждения и отмены
  записи среди действий нет: запись — только кнопкой «Подтвердить» или «да» на шаге
  подтверждения. Ошибка, лимит или неверный JSON — тот же разговор по правилам
  (`RuleInterpreter` + `triage.ts`). Новые проверки разговора — с мок-моделью, без API.
- Настройки — `src/bot/config.ts` (Zod), секреты только в `.env.local`; ошибки и журнал —
  без значений ключей и текста сообщений, VK ID маскируется (`maskId`).

## Каталог

- Схема — `src/catalog/schema.ts` (Zod, строгие объекты: неизвестные поля запрещены).
  Типы выводятся из схемы, отдельно их не описывать.
- Данные — TypeScript-модули в `src/content/`: `categories.ts`, `industries.ts`,
  `solutions/<id>.ts` (одно решение — один файл, плюс регистрация в `solutions/index.ts`).
- Каталог проверяется целиком при импорте `@/catalog` (`parseCatalog`): уникальность id,
  ссылки на категории и отрасли. Ошибка в данных ломает тесты.
- Категории и отрасли — независимые справочники. Пустой `industryIds` = любая отрасль.
- Цена: `{ kind: "fixed" | "from", amount, currency: "RUB" }` или `{ kind: "on_request" }`.
  `amount` — целое число в копейках (150 000 ₽ = `15000000`).
- Вид цены нельзя терять: «от» никогда не превращается в фиксированную цену
  (`getStartingPrice`, `formatPrice` в `src/catalog/price.ts`).
- Позиция будущей заявки — пара `(solutionId, packageId)`; id пакетов уникальны внутри решения.
- Адреса — только через `src/catalog/links.ts`: страница решения `solutionHref(id)` →
  `/catalog/<id>`, заявка `requestHref(solutionId, packageId)` →
  `/request?solution=…&package=…`. Параметры заявки проверяются по каталогу
  (`resolveRequestSelection`); неизвестное отбрасывается.
- Поиск и фильтры каталога — чистые функции в `src/catalog/search.ts`. Состояние хранится в URL:
  `/catalog?q=…&category=a&category=b&industry=x` (принимаются и значения через запятую,
  неизвестные id отбрасываются). Внутри группы — «или», между поиском, категориями и
  отраслями — «и». Поиск: все слова запроса в названии, кратком или полном описании
  (без учёта регистра и «ё»), а также в аудитории, задачах, возможностях и тегах.
- Каждое демонстрационное решение — `isDemo: true` (поле обязательное). Справочники
  категорий и отраслей `isDemo` не имеют.
- Статус зрелости `maturity` (`src/catalog/maturity.ts`): `demo` — демо-решение с пакетами
  (по умолчанию); `concept` — концепция, готового продукта нет; `in_development` — продукт
  в разработке, не подтверждён как готовый к промышленной эксплуатации. Пакеты обязательны
  только для `demo`; у остальных стоимость — «по запросу», сроки и цены не выдумываются.
  Статус показывается `MaturityBadge` в карточке, на странице решения и у консультанта.
- Описание решения: `audience` (для кого), `problems` (какие задачи решает),
  `capabilities` (возможности) — участвуют в поиске вместе с тегами.
- Перед добавлением решения проверяйте пересечения с существующими: близкие задачи
  объединяются в одну карточку (например, запись пациентов — часть ИИ-администратора
  клиники, распознавание документов — часть извлечения данных).

## Заявки

- Код — `src/requests/` и `src/app/request/`, подробности и чек-лист запуска — `docs/requests.md`.
- Сейчас **тестовый режим**: `TestRequestStore` отбрасывает данные. Реальное хранилище и
  приём включаются только отдельным решением после утверждения политики персональных
  данных и настройки инфраструктуры. Не создавать видимость работающего приёма.
- Одна Zod-схема на клиенте и сервере. Хранить минимум данных; IP — только как хэш с
  солью в памяти для ограничения частоты.
- Никогда не писать в логи имя, контакты и текст заявки — только id и режим.
- Не выдумывать реквизиты оператора и текст политики (`/privacy` — заглушка).

## Консультант

- Код — `src/consultant/`, `src/app/consultant/`, `src/components/consultant/`;
  подключение LLM — `docs/consultant.md`.
- Сейчас `MockChatProvider` — правила, не ИИ; интерфейс обязан это сообщать.
  Платные API и внешние LLM — только отдельным решением.
- Рекомендации: провайдер отдаёт только `solutionId` и причину, карточки и цены берутся
  из каталога (`resolveRecommendations`). Ссылки — через `src/catalog/links.ts`.
- Переписка не сохраняется и не логируется; email и телефоны скрываются до провайдера.
- Решения со статусом `concept` / `in_development` рекомендуются только с явной пометкой
  статуса в причине и ответе; выдавать их за готовые продукты нельзя.

## SEO и индексация

- Подробности и чек-лист открытия сайта — `docs/seo.md`.
- Индексация выключена по умолчанию: robots.txt `Disallow: /`, `noindex, nofollow` в
  метатегах и заголовке `X-Robots-Tag`. Включается при сборке только вместе:
  `SITE_URL=https://…` и `SITE_INDEXING=true`. Домен не выдумывать.
- Метаданные страниц — только через `pageMetadata()` (`src/lib/seo.ts`): title, description,
  canonical без параметров, Open Graph целиком (Next.js не сливает его с родительским),
  Twitter Card. Новая публичная страница добавляется в `INDEXABLE_PAGES` (sitemap).
- JSON-LD — только достоверные данные: `WebSite`, `BreadcrumbList`. Без `Organization`,
  `Product`/`Offer`, отзывов и рейтингов, пока нет реальных данных. Сериализация — `jsonLd()`.
- Концепции и продукты в разработке помечаются статусом в title и description
  (`src/catalog/seo.ts`).
- Сторонние счётчики, аналитика и пиксели не подключаются без отдельного решения.

## Безопасность и запуск

- Аудит, блокеры и планы (заявки, LLM) — `docs/production-readiness.md`; развёртывание —
  `docs/deployment-plan.md`; чек-лист — `docs/launch-checklist.md`. Публичный запуск —
  только решением владельца.
- Ключ клиента для ограничения частоты — только `src/lib/client-key.ts` (последний адрес
  `X-Forwarded-For`, хэш с солью). Не брать первый адрес: его подставляет клиент.
- Заголовки безопасности — `next.config.ts` (`SECURITY_HEADERS`); HSTS — на прокси.
- Ошибки страниц — `app/error.tsx` и `app/global-error.tsx`: без деталей для пользователя.

## Дизайн-система

- Стиль — «Витрина решений» в духе Liquid Glass. Основная (единственная) тема — тёмная:
  глубокий чёрный и графит (`color-scheme: dark`). Текст ≥ 4.5:1 к фону.
- Токены (цвета, стекло, шрифт, шкала текста, скругления, контейнер) — только в
  `src/app/globals.css`. Палитра Tailwind по умолчанию отключена: используйте `bg-surface`,
  `text-muted`, `text-accent` и т. п., не произвольные цвета.
- Стекло — утилиты `glass`, `glass-hover`, `glass-bar`; главное действие — `liquid-primary`.
  Стекло применяется к кнопкам и навигации; карточки — плотные графитовые поверхности
  (`Card`) ради читаемости. Кнопки — pill (`rounded-control` = 9999px).
- Пишите только стандартный `backdrop-filter`: префикс добавляет сборщик. Ручной
  `-webkit-backdrop-filter` рядом с ним сборщик сливает в один префиксный, и Chromium
  перестаёт размывать.
- Учитываются `prefers-reduced-motion` и `prefers-reduced-transparency` (стекло становится плотным).
- Шрифт Onest (`src/app/fonts.ts`, `next/font/google`, кириллица).
- Базовые компоненты — `src/components/ui/`, каркас — `src/components/layout/`.
  Навигация задаётся одним списком в `src/config/navigation.ts`; у каждого адреса должна быть страница.
- `cn()` не сливает конфликтующие классы: не переопределяйте `display`/отступы компонента
  через `className` — оборачивайте или добавляйте вариант.
- Цены выводятся только через `PriceTag` / `formatPrice`, вид цены не теряется.
- Демо-данные помечаются `DemoBadge`; демо-полоса присутствует на всех страницах.
- `/ui` — служебная витрина компонентов, доступна только в режиме разработки.

## Тексты сайта

- Тексты главной и информационных страниц — `src/content/approach.ts` (этапы работы,
  принципы) и `src/content/directions.ts` (направления → фильтры каталога).
- Описываем формат работы, а не результаты: без цифр, процентов, гарантий, отзывов,
  кейсов, клиентов и истории компании. Тест `src/content/pages.test.ts` это проверяет.
- Числа решений в блоках считаются по каталогу (`filterSolutions`), а не пишутся вручную.

## Процесс и Git

- Приватный GitHub-репозиторий `ai-solutions-store`. Одна ветка на этап, PR в `main`.
- Merge выполняет владелец; после merge ставится тег `stage-N`.
- `package-lock.json` всегда в Git; установка в CI — `npm ci`.
- Push — в конце каждой сессии (после подтверждения владельца).

## Обязательные проверки перед PR

```
npm run lint
npm run typecheck
npm test
npm run format:check
npm run build
```

Те же шаги выполняет CI (`.github/workflows/ci.yml`) на ubuntu-latest и windows-latest.
Проверка в Linux/CI не заменяет ручную проверку на Windows-машине владельца.
