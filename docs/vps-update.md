# Обновление существующего VPS (`/opt/ai-solutions-store`)

Скрипт `deploy/vps-update.sh` обновляет прежнее развёртывание: одно приложение в
`/opt/ai-solutions-store`, службы systemd для бота и панели, база SQLite (WAL) в `.data`.
Экземпляры клиник из `deploy/clinic` обновляются иначе — через `new-clinic.sh`.

Скрипт рассчитан только на обновление без изменения схемы базы. Если в целевом коммите
есть миграции, он остановится, ничего не изменив.

## Что делает `update <коммит> [<текущий коммит>]`

1. **Проверки без изменений.** Если что-то не так, скрипт останавливается и ничего не
   меняет. Он проверяет:
   - находит юниты systemd, которые запускают код из каталога, — ровно одну службу бота
     и одну службу панели (pm2 не поддерживается);
   - на сервере стоит ожидаемый коммит (по умолчанию `47323c6`), а целевой его продолжает;
   - в файлах из Git нет локальных правок;
   - схема базы не меняется;
   - обе службы работают;
   - `BOT_MODE` пуст или `demo`, `VK_ALLOWED_USER_IDS` задан;
   - хватает места;
   - коды ответов адресов: панель напрямую и домены из `nginx -T` через 127.0.0.1;
     российский прокси не затрагивается.
2. **Копии без остановки служб** — в `/root/demo-med-backups/<время>/`, доступ только root:
   - `config/`: `.env.local`, юниты и их EnvironmentFile, `/etc/nginx`, права файлов;
     имена ключей `.env.local` без значений — в `env-keys.txt`;
   - код целиком, без `.data`, в каталог отката `/opt/ai-solutions-store.prev-<коммит>-<время>`;
   - предварительная копия базы `db-online.sqlite` (`VACUUM INTO`).
3. **Остановка служб** и согласованная копия базы `db-before-update.sqlite` через
   `VACUUM INTO`, с учётом WAL. Затем проверки копии:
   - совпадает с рабочей базой (`integrity_check`, версия схемы, число строк каждой
     таблицы);
   - восстанавливается: её временный экземпляр открывается кодом приложения.

   Контрольные суммы — в `SHA256SUMS`.

4. **Обновление кода.** От имени владельца каталога: `git checkout --detach <коммит>`,
   `npm ci`, `npm run build`. Затем новый код проверяет настройки бота в окружении его
   службы: должны приниматься, режим — `demo`. И проверяется, что база не изменилась.
5. **Запуск и проверки:**
   - панель отвечает 200 на `/admin/login`;
   - бот пишет в журнал `long poll: connected`;
   - коды ответов всех адресов совпадают с прежними (в том числе `/miniapp` и
     `/api/miniapp/clinic`).

**Сбой после остановки служб** — автоматический откат кода:

- копия базы `db-before-rollback.sqlite`;
- код возвращается из каталога отката, `.data` не затрагивается;
- службы запускаются, проверки выполняются снова.

Рабочая база не пересоздаётся и автоматически из копии не восстанавливается.
Журнал — `update.log` в каталоге копий.

## Откат после успешного обновления

```bash
sudo bash /root/demo-med-backups/<время>/vps-update.sh rollback /opt/ai-solutions-store.prev-47323c6-<время>
```

Код вернётся к `47323c6`, база останется текущей. Это безопасно: схема та же (v8), а новая
версия хранит данные в тех же таблицах. Восстанавливать базу из
`db-before-update.sqlite` нужно только при её повреждении, и тогда теряется всё, что
появилось после обновления:

1. Остановить службы.
2. Переименовать `bot.sqlite`, `-wal` и `-shm`, не удаляя их.
3. Скопировать копию на место `bot.sqlite` с прежним владельцем и правами
   (`config/permissions.txt`).
4. Запустить службы.

## Проверено

Репетиция в облаке на копии развёртывания `47323c6`: отдельный владелец каталога, службы
через заглушку `systemctl`, вымышленная база v8. Три сценария:

- сбой новой версии после запуска → автооткат;
- успешное обновление: простой ≈ 40 с, вход в панель учётной записью из старой версии;
- ручной откат.

На настоящем сервере с systemd и nginx скрипт не запускался.
