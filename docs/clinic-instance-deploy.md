# Отдельный экземпляр системы для новой клиники

Задача P0-7 (`docs/first-client-roadmap.md`). Одна клиника — один экземпляр: свои
процессы бота и панели, системный пользователь, база SQLite, секреты, каталоги,
журналы и домен. Код (выпуск) — один на сервер, только для чтения. Docker и
дополнительные сервисы не нужны.

Действующий демо-стенд на VPS этим не затрагивается: он работает из своего каталога со
своим `.env.local`. Новые клиники ставятся рядом, по раскладке ниже.

## 1. Раскладка на сервере

| Что                         | Где                                                                                       | Права                                        |
| --------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------- |
| Выпуск кода (общий)         | `/opt/demo-med/releases/<коммит>`, ссылка `current`                                       | владелец `demo-med`, остальным только чтение |
| Настройки и секреты клиники | `/etc/demo-med/clinics/<id>.env`                                                          | `600 root` — читает только systemd           |
| База клиники                | `/var/lib/demo-med/<id>/bot.sqlite`                                                       | каталог `700 dm-<id>`, файлы `600`           |
| Резервные копии клиники     | `/var/backups/demo-med/<id>/`                                                             | `700 dm-<id>`                                |
| Сервисы                     | `demo-med-bot@<id>`, `demo-med-panel@<id>`                                                | пользователь `dm-<id>`                       |
| Журналы                     | `journalctl -u demo-med-bot@<id> -u demo-med-panel@<id>`                                  | идентификаторы `demo-med-<id>-bot/-panel`    |
| nginx                       | `/etc/nginx/sites-available/demo-med-<id>.conf`, журналы `/var/log/nginx/demo-med-<id>.*` | —                                            |

Файлы в репозитории:

- `deploy/clinic/clinic.env.example` — шаблон настроек (секреты пустые);
- `deploy/clinic/new-clinic.sh` — создание, проверка, nginx, владелец, запуск;
- `deploy/systemd/demo-med-bot@.service`, `demo-med-panel@.service` — шаблоны сервисов;
- `deploy/nginx/clinic.conf.template` — шаблон nginx;
- `scripts/clinic-instance.mts` (`npm run clinic -- …`) — проверка настроек и nginx.

## 2. Изоляция

- **Процессы:** у каждой клиники свой пользователь `dm-<id>` без входа в систему; сервисы
  systemd с `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`,
  `UMask=0077`. Писать можно только в `/var/lib/demo-med/<id>`; код — только чтение.
- **Данные:** у каждой клиники своя база в своём каталоге (`700`). Пользователь другой
  клиники не может ни прочитать её, ни увидеть список клиник (`/var/lib/demo-med` — `711`).
- **Секреты:** файл настроек `600 root`, значения передаёт systemd; в аргументы команд,
  журналы и вывод проверок они не попадают. Свой `MEDICAL_DATA_KEY` генерируется при
  создании. Проверка запрещает одинаковые ключи, токены, сообщества, порты, домены и
  базы у двух клиник.
- **Общий код без общих настроек:** Next.js и бот читают `.env*` из каталога запуска —
  поэтому в каталоге выпуска их быть не должно (проверка до запуска это контролирует).
  `npm run bot:setup` для клиник не используется: он пишет `.env.local`.
- **Сеть:** панель слушает только `127.0.0.1:<PANEL_PORT>` (свой порт 3100–3999); наружу —
  nginx с https, только `/admin`, `/api/admin`, `/_next`, `/miniapp`, `/api/miniapp`.
- **Сессии и сотрудники** — в базе клиники: вход в панель одной клиники не действует в
  другой (проверено тестом `src/deploy/instance.test.ts`).

## 3. Подготовка сервера (один раз)

Под root; значения в `<…>` — свои.

```bash
# Пользователь кода и каталоги
useradd --system --create-home --home-dir /opt/demo-med --shell /usr/sbin/nologin demo-med
install -d -m 0755 -o demo-med -g demo-med /opt/demo-med/releases

# Выпуск: код коммита без .git и без .env, зависимости, сборка
sha=<коммит>
sudo -u demo-med install -d /opt/demo-med/releases/$sha
git -C <клон репозитория> archive "$sha" | sudo -u demo-med tar -x -C /opt/demo-med/releases/$sha
cd /opt/demo-med/releases/$sha
sudo -u demo-med npm ci
sudo -u demo-med NODE_OPTIONS=--max-old-space-size=1024 npm run build   # swap — admin-panel-deploy.md, раздел 4
ls -a | grep '^\.env' && echo "УДАЛИТЕ .env* из выпуска"                  # должно быть пусто, кроме .env.example
ln -sfn /opt/demo-med/releases/$sha /opt/demo-med/current

# Шаблоны сервисов
install -m 0644 deploy/systemd/demo-med-bot@.service deploy/systemd/demo-med-panel@.service /etc/systemd/system/
systemctl daemon-reload
```

Обновление выпуска — те же шаги в новый каталог, затем резервные копии всех клиник
(`new-clinic.sh backup <id>`), переключение `current` и `systemctl restart
'demo-med-*@*'`. Откат — `current` на прежний каталог и перезапуск. Выпуск общий: новая
версия действует сразу для всех клиник.

## 4. Чек-лист подключения клиники

Все команды — под root из `/opt/demo-med/current`; `<id>` — например `clinic-ivanov`.

**1. Создание экземпляра.**

```bash
deploy/clinic/new-clinic.sh create <id> <порт 3100–3999> <домен панели>
```

Создаёт пользователя `dm-<id>`, каталоги данных и копий, файл настроек с новым
`MEDICAL_DATA_KEY`. Ничего существующего не перезаписывает; порт и домен сверяются с
другими клиниками. Копию `MEDICAL_DATA_KEY` сохраните отдельно от резервных копий базы
(без ключа зашифрованные сведения не прочитать).

**2. Настройки.** `sudoedit /etc/demo-med/clinics/<id>.env`:

- `VK_GROUP_ID`, `VK_GROUP_TOKEN` — сообщество клиники и его ключ (права «Сообщения
  сообщества»); в сообществе включить сообщения, возможности ботов и Bots Long Poll
  (события `message_new`, `message_event`, `message_reply`) — вручную в настройках ВКонтакте;
- `VK_ALLOWED_USER_IDS` — VK ID тестировщиков (пока заполнено, бот отвечает только им);
- `VK_ADMIN_USER_ID` — администратор клиники для уведомлений;
- `BOT_MODE=live` (по шаблону);
- `OPENAI_API_KEY` — только после решения юриста о передаче текста во внешний ИИ;
- `TRUSTED_PROXY_IPS` — если перед nginx есть прокси (раздел 5).

**3. Проверка до запуска.**

```bash
deploy/clinic/new-clinic.sh check <id>
```

Обязательные переменные, незаменённые заполнители, права файла, путь базы, `.env` в
выпуске, https-cookie, Mini App, конфликты с другими клиниками. `FAIL` — запускать
нельзя; `WARN` — прочитать. Значения не выводятся. Та же проверка выполняется перед
каждым запуском сервиса (`ExecStartPre`): ошибочные настройки не дадут сервису стартовать.

**4. Подключение ВКонтакте.** `deploy/clinic/new-clinic.sh vk <id>` — ключ подходит к
сообществу, Long Poll включён (ничего не отправляет).

**5. Домен и https.** DNS домена панели → этот сервер (делает владелец), затем:

```bash
deploy/clinic/new-clinic.sh nginx <id> --http-only
certbot certonly --webroot -w /var/www/letsencrypt -d <домен панели>
deploy/clinic/new-clinic.sh nginx <id>
```

При ошибке `nginx -t` скрипт возвращает прежнюю конфигурацию — другие клиники не
затрагиваются.

**6. Панель и владелец.**

```bash
deploy/clinic/new-clinic.sh start <id> panel
deploy/clinic/new-clinic.sh owner <id> <логин владельца>     # пароль вводится скрыто
```

Остальных сотрудников владелец приглашает в панели («Сотрудники»).

**7. Справочник.** В панели `https://<домен>/admin`: название, адрес, телефон, режим
работы, как добраться, памятка; специальности и врачи (с часами приёма); услуги — из CSV
(«Настройки» → «Загрузка прайса»). Демо-данные новой базы заменить или отключить: в
режиме `live` бот не запустится, пока они остались (он перечислит поля).

**8. Бот на разрешённых аккаунтах.**

```bash
deploy/clinic/new-clinic.sh start <id> bot
deploy/clinic/new-clinic.sh status <id>
```

С аккаунтов из `VK_ALLOWED_USER_IDS`: приветствие без «демо», цены, врачи, адрес, запись и
отмена, вопрос о специалисте, которого нет, «позвать администратора» (уведомление пришло
`VK_ADMIN_USER_ID`), запись видна в панели. Посторонний аккаунт получает «бот клиники пока
проходит проверку».

**8а. Резервные копии.** `docs/backup-restore.md`, раздел 3: `backup-init`, ключи — вне
сервера, хранилище, `backup-check`, `backup`, `backup-verify`, `backup-enable`. До
открытия доступа пациентам копии должны работать.

**9. Открытие доступа.** Резервная копия (`new-clinic.sh backup <id>`), затем в файле
настроек очистить `VK_ALLOWED_USER_IDS`, `new-clinic.sh check <id>` (предупреждение «бот
отвечает всем пациентам» — ожидаемо), `systemctl restart demo-med-bot@<id>`. Проверить с
постороннего аккаунта.

## 5. Особенности

- **`BOT_MODE=live`:** тексты без пометок «демо», доступ всем при пустом
  `VK_ALLOWED_USER_IDS`, запуск бота запрещён, пока в справочнике данные вымышленной
  клиники (`src/bot/clinic/live-check.ts`). Поэтому панель запускается раньше бота.
- **Mini App:** при открытом доступе бота `VK_MINIAPP_ID` не задаётся — Mini App пока
  только для тестовых аккаунтов (проверка это запрещает). Для теста — `VK_MINIAPP_ID`,
  `VK_MINIAPP_SECRET`, `MINIAPP_ALLOWED_USER_IDS`; своё приложение VK на каждую клинику
  (адрес приложения — `https://<домен>/miniapp`). Строка запуска не пишется в журнал
  nginx (`access_log off`).
- **Адрес клиента за nginx:** приложение берёт последний адрес `X-Forwarded-For`
  (ограничения попыток входа). nginx перезаписывает его `$remote_addr`. Если перед nginx
  стоит доверенный прокси (например, российский для Mini App), его адреса — в
  `TRUSTED_PROXY_IPS`: nginx возьмёт адрес клиента из его заголовка (`real_ip`), иначе все
  пациенты будут выглядеть одним адресом.
- **Ресурсы:** бот ~100 МБ, панель ~150–250 МБ на клинику (`MemoryMax` 400 и 600 МБ).
  Сборка — одна на выпуск. Оценка числа клиник на сервер — `docs/scaling-plan.md`.

## 6. Что не автоматизировано

- DNS, сертификат (команда certbot — вручную), настройки сообщества ВКонтакте и
  приложения VK Mini Apps;
- заполнение секретов в файле настроек;
- заполнение справочника клиники и тест с телефона;
- мониторинг и уведомления — `docs/monitoring.md` (один раз на сервер); резервные копии —
  `docs/backup-restore.md`
  (зашифрованные, во внешнее хранилище, ежедневный таймер; хранилище выбирает владелец).
