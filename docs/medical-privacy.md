# Медицинская конфиденциальность и разграничение доступа

Этап 2 админ-панели и VK-бота вымышленной клиники «Демо-Мед». Документ описывает, что
реально защищено, что **не** защищено и что нужно для следующего шага. Главное правило —
никаких обещаний конфиденциальности, которых система не обеспечивает.

## 1. Блокирующая проблема: переписка во ВКонтакте

**Руководители сообщества ВКонтакте (владелец, администраторы, редакторы с доступом к
сообщениям) видят всю переписку пациента с сообществом в интерфейсе ВКонтакте** —
включая всё, что пациент написал боту о самочувствии. Ссылка из уведомления
`https://vk.com/gim<ID>?sel=<peer>` просто открывает этот диалог. Это свойство ВКонтакте:
ни роли нашей панели, ни шифрование базы этого не ограничивают.

Поэтому:

- разграничение доступа в панели защищает **только данные в нашей базе и в нашем API**;
- **конфиденциальность медицинских сведений внутри ВКонтакте не обеспечена** — это
  блокирующая проблема для работы с реальными пациентами;
- бот этого не скрывает: в приветствии и перед передачей администратору он прямо говорит,
  что переписку могут читать администраторы сообщества.

Насколько нам известно, ограничить руководителю сообщества чтение отдельных диалогов
нельзя: доступ к сообщениям сообщества даётся ролью целиком. Из контейнера разработки
VK недоступен, поэтому это **не проверено** вживую — сверить с dev.vk.com и настройками
сообщества («Управление → Участники → Руководители»). Вывод не меняется, пока не доказано
обратное: считать переписку видимой.

### Предлагаемое изменение архитектуры

1. **Медицинская часть разговора — вне ВКонтакте.** ВКонтакте остаётся каналом записи
   и организационных вопросов (направление, время, адрес, отмена). Для описания жалобы
   бот выдаёт одноразовую ссылку (токен на 15–30 минут, привязан к записи) на защищённую
   форму или чат на домене клиники: https, без сторонних счётчиков, данные сразу
   шифруются ключом `MEDICAL_DATA_KEY`, доступ — только врачу записи по согласию,
   по той же схеме, что уже реализована (`disclosure_consents`, журнал доступа).
2. **Режим «без медицинских вопросов» во ВКонтакте:** `BOT_MEDICAL_QUESTIONS=false` уже
   реализован — бот не расспрашивает о травме, длительности и тревожных признаках, а
   сразу предлагает направление. Тревожные признаки по-прежнему проверяются правилами
   (при экстренных — 103/112). Пока нет защищённой формы, для реальных пациентов
   рекомендуется именно этот режим.
3. **Минимум руководителей сообщества** с доступом к сообщениям. Администраторы клиники
   отвечают пациентам только через будущий интерфейс панели (ответ уходит через VK API
   от имени сообщества), а не через «Сообщения сообщества». Роль «Администратор» в
   сообществе ВКонтакте остаётся у одного ответственного лица, а это прописывается в
   регламенте клиники.
4. **Удаление переписки** в сообщениях сообщества после записи — вручную или через
   VK API (возможности и ограничения `messages.delete` для сообщества проверить на
   dev.vk.com; у пациента сообщения в любом случае остаются). Это снижает, но не
   устраняет риск.

Пока пункт 1 не реализован, внутри ВКонтакте медицинские сведения **не защищены** от
руководителей сообщества.

## 2. Роли панели

Права задаются одной таблицей `src/admin/permissions.ts` и проверяются на сервере для
каждого запроса API (`src/admin/api.ts`, таблица `ROUTES`) и для каждой страницы
(`requirePage`). Скрытие разделов в меню — только удобство.

| Что                                                           | owner (владелец) | admin (администратор) | doctor (врач)                   |
| ------------------------------------------------------------- | ---------------- | --------------------- | ------------------------------- |
| Главная: записи на сегодня, счётчики бота (без текста)        | да               | да                    | нет                             |
| Все записи: номер, врач, время, статус, источник, маска VK ID | да               | да                    | нет                             |
| Создание, перенос, отмена записей                             | да               | да                    | нет                             |
| Врачи, специальности, расписание                              | да               | да                    | нет                             |
| Настройки клиники, услуги и цены                              | да               | нет                   | нет                             |
| Сотрудники, роли, приглашения                                 | да               | нет                   | нет                             |
| Журнал доступа к сведениям (только метаданные)                | да               | нет                   | нет                             |
| «Мои приёмы» — записи к своему врачу расписания               | нет              | нет                   | да                              |
| Описание жалобы пациента                                      | **никогда**      | **никогда**           | только своей записи по согласию |
| Переписка с ботом, история сообщений, состояние диалога       | нет              | нет                   | нет                             |

Ни одна роль сама по себе не открывает медицинские сведения. В API нет маршрута, который
отдаёт переписку, историю реплик или JSON-состояние диалога.

Медицинскими считаются: жалоба и её описание, ответы на уточнения (травма, длительность,
тревожные признаки), реплики разговора. Организационные: номер записи, врач,
специальность, дата и время, статус, источник, маска VK ID (`ВКонтакте, id…123`).

### Где ещё могла бы быть утечка и что сделано

- **Пометка записи** (`note`) видна всем администраторам. Сервер отклоняет пометки с
  жалобами, симптомами, тревожными признаками, телефонами и адресами почты
  (`noteProblem` в `src/admin/schemas.ts`). Проверка эвристическая: очевидное ловит, но
  не всё — поэтому в интерфейсе есть подсказка. Врачу пометка не показывается.
- **Поиск** по записям ищет по номеру и пометке; медицинских полей в таблице записей нет.
- **Журналы** (`console`, `admin_audit`, `medical_access_log`, `stats`) — только действие,
  id и результат. Ошибки API пишутся без тела запроса.
- **Уведомление администратору** о handoff содержит только ссылку на диалог.
- **Ответы API** врачу: список «Мои приёмы» содержит только признак «сведения переданы»;
  содержание — отдельным запросом, который пишется в журнал доступа.

## 3. Как врач получает доступ к сведениям пациента

1. Пациент записался через бота. Если в разговоре была жалоба и на сервере задан
   `MEDICAL_DATA_KEY`, к подтверждению записи добавляется необязательная кнопка
   «Передать врачу описание».
2. По кнопке бот показывает **дословно**, что уйдёт врачу (область, описание до 160
   символов, травма, длительность, тревожные признаки), кому (врач этой записи), зачем
   (подготовка к приёму) и на какой срок. Ничего не передано.
3. «Передать врачу» — создаётся согласие в `disclosure_consents`: одна запись, один
   получатель (`recipient_doctor_id` — врач записи из базы, не из кнопки), цель, срок
   (дата приёма + 7 дней). Содержимое шифруется AES-256-GCM, контекст — номер согласия.
   «Не передавать» — описание удаляется из памяти бота.
4. Врач с учётной записью, связанной с этим врачом расписания, видит в «Мои приёмы»
   отметку и открывает сведения. Сервер проверяет: роль `doctor`; запись к его врачу;
   запись не отменена; есть действующее согласие именно для этого врача. Каждая попытка
   (успешная и отказ) — в `medical_access_log`.
5. Доступ прекращается: отзыв пациентом («Мои записи» → «Отозвать сведения №…»),
   отмена записи (пациентом или в панели), перенос к другому врачу, истечение срока.
   Содержимое при этом удаляется (`payload = NULL`).

Ограничения схемы:

- **VK ID не доказывает личность.** Сведения помечены «со слов собеседника ВКонтакте,
  личность не подтверждена, не медицинский документ».
- Связь «учётная запись ↔ врач расписания» задаёт владелец. Владелец технически может
  пригласить сотрудника с ролью врача (или создать вторую учётную запись) и так получить
  доступ к сведениям пациентов этого врача. Защита — журнал действий (`admin_audit`:
  кто выдал роль), журнал доступа и организационный регламент; техническая защита от
  злоупотребления владельцем — второе лицо, утверждающее привязку врача (следующий этап).
- Переписка целиком врачу не передаётся никогда.

## 4. Шифрование базы

`MEDICAL_DATA_KEY` (32 байта, base64) шифрует:

- состояние разговоров (`sessions.state`: жалоба, ответы, последние реплики);
- содержимое согласий (`disclosure_consents.payload`).

Что это даёт: копия базы, резервная копия или файл, вынесенный с сервера, без ключа не
раскрывают медицинские сведения. Чего это **не** даёт: администратор сервера, у которого
есть и база, и `.env.local`, может расшифровать всё. Ключ храните отдельно от резервных
копий базы. Потеря ключа — потеря зашифрованных разговоров (бот начнёт их заново) и
переданных сведений; записи на приём не зашифрованы и не пострадают.

Без ключа: разговоры хранятся как раньше (открытым текстом, 24 часа), передача врачу
выключена, `npm run bot:check` об этом предупреждает.

## 5. Остальные ограничения конфиденциальности

- **ВКонтакте** — см. раздел 1 (блокирующая).
- **OpenAI.** При заданном `OPENAI_API_KEY` текст сообщения (с удалёнными телефонами и
  почтой) и краткая память разговора уходят в OpenAI. Это передача третьему лицу; для
  реальных пациентов нужна правовая оценка или режим без OpenAI.
- **Администратор сервера** имеет доступ ко всему (база + ключ).
- **Тексты сообщений** пациента ВКонтакте хранит у себя независимо от нас.
- **Ограничение попыток входа** хранится в памяти процесса панели.
- Данные клиники и пациентов в проекте вымышленные; реальные персональные данные не
  собираются до правовой оценки (AGENTS.md).

## 6. Следующий этап: явное согласие пациента на передачу администратору

Схема уже готова: `disclosure_consents.recipient_role` допускает `admin`, есть `scope`,
`purpose`, `expires_at`, статусы `granted / revoked / expired`, журнал доступа. **Код
согласий для администратора не создаёт и не читает** — `countActive("admin")` всегда 0
(проверяется тестом). Для реализации нужно:

1. Определить **фрагмент**: не «вся переписка», а выбранные пациентом сообщения или
   краткое описание, показанное ему дословно до согласия (как для врача).
2. Определить **получателя**: конкретная учётная запись или роль на ограниченный срок;
   цель — например, «перенос записи по состоянию здоровья».
3. **Отказ без раскрытия**: при отказе администратор видит только «пациент не дал
   согласия», без причин и содержания.
4. **Отзыв** в любой момент из диалога; содержимое удаляется сразу.
5. **Журнал доступа** — уже есть; добавить просмотр журнала пациенту по запросу.
6. Канал: пока переписка идёт во ВКонтакте, руководители сообщества видят её и без
   согласия (раздел 1) — поэтому согласие для администратора имеет смысл только после
   переноса медицинской части в собственный канал клиники.
7. Правовая оценка: согласие на обработку специальной категории персональных данных,
   политика, сроки хранения.

Автоматических разрешений нет и быть не должно: согласие создаётся только действием
пациента.

## 7. Проверки

`src/admin/privacy.test.ts` — права ролей; администратор и владелец не читают сведения;
врач не видит чужих пациентов; прямые запросы, перебор номеров и путей; отмена, перенос и
отзыв закрывают доступ; смена роли завершает сессии; приглашения; уведомления, журналы и
аудит без медицинских данных; шифрование; миграция v5 → v6 с сохранением пароля и сессии;
запись через бота; одновременная запись; отсутствие согласий по умолчанию; handoff.
