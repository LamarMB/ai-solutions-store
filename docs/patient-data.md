# Запрос пациента о своих данных: выгрузка и удаление по VK ID

Задача P0-11 (`docs/first-client-roadmap.md`). Панель → «Данные пациента», только роль
`owner` (право `patient_data.manage`). Работает в базе своей клиники: у каждой клиники
отдельный экземпляр и отдельная база (`docs/clinic-instance-deploy.md`), поэтому данные
другой клиники недоступны.

Сроки ответа на запрос, основания отказа или хранения и форма запроса определяет клиника
вместе с юристом. Здесь — только техническая сторона.

## 1. Что хранится о пациенте и что выгружается

| Категория                                                         | В выгрузке JSON                                                                            | Удаление                                     |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------- |
| Записи на приём (бот, Mini App)                                   | номер, врач, дата, время, статус, источник, даты создания и отмены, пометка администратора | удаляются; предстоящие — слоты освобождаются |
| Разговор с ботом (память, реплики)                                | только «хранится» и дата обновления                                                        | удаляется                                    |
| Согласия на передачу сведений врачу                               | номер записи, получатель, цель, статус, даты; «сведения хранятся» — да/нет                 | удаляются вместе со сведениями               |
| Обращения к администратору                                        | статус, версия согласия, даты; «текст хранится» — да/нет                                   | удаляются вместе с текстом                   |
| Пауза бота, служебные уведомления, отметки обработанных сообщений | пауза и уведомления — да; отметки — только количество                                      | удаляются                                    |

**Не выгружается через панель:** содержимое разговора, сведения для врача и тексты
обращений. Это медицинские сведения, а их владелец и администратор не получают ни через
один API (`docs/medical-privacy.md`). Если пациенту нужна их копия, решение о способе
выдачи (и о том, кто её готовит) — за клиникой и юристом. Разговор и так хранится не
дольше `BOT_HISTORY_HOURS`.

Выгрузка — файл `patient-data-<дата>.json` (формат `demo-med-patient-data`, версия 1)
скачивается в браузере владельца. Передавать его пациенту — защищённым способом, который
определит клиника.

## 2. Удаление

1. Найти пациента по VK ID. Панель покажет количество записей по каждой категории, что не
   выгружается и что **сохранится** после удаления.
2. «Удалить данные пациента…» → в окне ещё раз ввести VK ID → «Удалить безвозвратно».
   «Не удалять» или закрытие окна ничего не меняют.
3. Сервер удаляет только если:
   - VK ID введён повторно и совпадает;
   - данные не изменились после предпросмотра (иначе ответ «проверьте ещё раз»).
4. Всё удаляется одной транзакцией: при сбое не удаляется ничего. Другие пациенты не
   затрагиваются.

**Сохраняется (показывается до подтверждения):**

- **Журналы доступа к сведениям и открытия обращений, журнал действий по записям.** Там
  только номер записи или обращения, дата и действие, без VK ID и содержания. Они нужны
  для подотчётности доступа.
- **Переписка в сообщениях сообщества ВКонтакте.** Она хранится во ВКонтакте; удалить её
  может руководитель сообщества в интерфейсе ВКонтакте.
- **Текст, отправленный во внешний ИИ-сервис (если подключён).** Он хранится по условиям
  провайдера.
- **Отметки обработанных нажатий кнопок.** Они не связаны с VK ID и удаляются через 3 суток.
- **Зашифрованные резервные копии** — раздел 3.

**Журнал действий:** `patient_export` и `patient_erase` с количеством удалённого по
категориям, без VK ID. Учёт самих запросов пациентов (кто, когда, что сделано) клиника
ведёт у себя: в системе VK ID удалённого пациента не остаётся.

## 3. Резервные копии

Удалённые данные остаются в зашифрованных копиях (`docs/backup-restore.md`), пока те не
удалятся по сроку хранения (`BACKUP_KEEP` копий во внешнем хранилище, `BACKUP_LOCAL_KEEP` —
на сервере). Изменить копии нельзя: они зашифрованы и проверены целиком.

**При восстановлении копии, сделанной до удаления,** данные этих пациентов вернутся в базу.
Сразу после восстановления, до открытия доступа сотрудникам, владелец повторяет удаление
по каждому VK ID из своего учёта запросов, сделанных после даты копии. Без такого учёта
система не знает, кого удалять повторно: VK ID удалённых пациентов в ней не хранится.

## 4. Ограничения

- Удаление необратимо (кроме восстановления старой копии; см. раздел 3).
- Пациент может написать боту снова: появятся новые данные. Это новый разговор, не
  восстановление старого.
- Поиск — только по VK ID. По имени или телефону искать нельзя: эти данные система не
  хранит.

## 5. Сквозная проверка в браузере

`npm run e2e:patient-flow` (`scripts/e2e/patient-flow.mjs`) — путь целиком, через интерфейс:

1. Пациент записывается через VK Mini App и видит запись в «Моих записях».
2. Запись видна в панели: источник «VK Mini App», VK ID скрыт.
3. Владелец находит пациента и скачивает JSON; в нём эта запись, нет чужих записей и
   медицинского содержимого.
4. «Не удалять» ничего не меняет.
5. Удаление с повторным вводом VK ID.
6. Именно тот забронированный слот (его дата и время) снова свободен — в API и в Mini App.
7. Запись другого пациента цела; ошибок в консоли, ответов ≥ 400 и VK ID в адресах
   запросов панели нет.

Окружение создаётся на один запуск и удаляется в любом случае, в том числе при ошибке и
Ctrl+C:

- новая база в системном временном каталоге;
- вымышленная клиника «Демо-Мед» и пациенты 900100 и 900777;
- случайные ключи и пароль владельца;
- `next start` на 127.0.0.1 со случайным портом.

ВКонтакте, VPS и рабочие базы не используются. Явные переменные окружения сценария
важнее `.env.local`.

**Что нужно:**

- сборка `npm run build` (сценарий проверяет её наличие; после изменений кода
  пересоберите);
- Playwright с Chromium — он не входит в зависимости проекта:
  `npm i --no-save playwright && npx playwright install chromium`, или глобальная установка.
  Свой Chromium указывается в `E2E_CHROMIUM_PATH`.

**Результат** — в `.data/e2e/patient-flow-<время>/`, в Git не попадает:

- при успехе — только `report.json`; `E2E_KEEP_SHOTS=1` сохраняет и снимки экранов;
- при падении — отчёт, снимки по шагам, снимки обеих страниц в момент сбоя и журнал
  сервера.

Код выхода: 0 — пройден, 1 — ошибка, 130 — прерван. В CI и `npm test` не входит, так как
нужны сборка и браузер.
