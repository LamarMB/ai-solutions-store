# Публикация продающего сайта через nginx VPS

Скрипт `deploy/site-publish.sh` открывает публичные страницы сайта на существующем
домене. Панель (`/admin`, `/api/admin`) и Mini App (`/miniapp`, `/api/miniapp`) работают
как прежде, всё остальное по-прежнему отвечает 404.

## Почему был 404

По инструкции развёртывания (`docs/admin-panel-deploy.md`, раздел 9) в server-блоке
домена стоит `location / { return 404; }`. Наружу открыты только `/admin`, `/_next` и
`/miniapp`.

Если `location = /` вносили в `/etc/nginx/sites-available/clinic-admin`, а nginx читает
другой файл — 404 остаётся, хотя `nginx -t` проходит. Так бывает, когда в
`sites-enabled` лежит копия, а не ссылка, или когда для домена есть другой блок на 443
(certbot, `conf.d`). Скрипт определяет действующий блок по `nginx -T`, а не по имени
файла.

Одного `location = /` и так недостаточно: без `/catalog`, `/privacy`, `/demo/*`, иконок и
`robots.txt` сайт неполный.

## Что делает `apply`

1. **Диагностика.** Загруженные файлы, `sites-enabled`, все server-блоки домена на 443
   (какой действует), его `location` и причина 404.
2. **Копия.** Изменяемый файл и весь `/etc/nginx` — в `/root/demo-med-backups/site-<время>/`.
3. **Правка.** В действующем блоке `location / { return 404; }` (и `location = /`,
   оставшийся от ручных попыток) заменяется на `include /etc/nginx/snippets/demo-med-site.conf`.
   В сниппете:
   - `/`;
   - `/catalog`, `/consultant`, `/how-we-work`, `/about`, `/privacy`, `/request`;
   - `/robots.txt`, `/sitemap.xml`, иконки, `/og-image.png`, `/demo/*`;
   - `location / { return 404; }` для всего остального.

   Адрес приложения берётся из существующего `proxy_pass` у `/admin` или `/miniapp`.

4. **Проверки.** `nginx -t`, перезагрузка, HTTPS-проверки через nginx этого сервера:
   - публичные страницы и ресурс `/_next/static` — 200, главная отдаёт страницу сайта;
   - `/ui`, `/api`, `/api/requests`, `/.env`, `/.git/config`, `/server-status` — 404;
   - `/admin`, `/admin/login`, `/api/admin/dashboard`, `/miniapp`, `/api/miniapp/clinic`
     отвечают так же, как до изменения.
5. **Откат.** Любая ошибка — файл восстанавливается из копии, сниппеты удаляются,
   nginx перезагружается.

**Скрипт останавливается, ничего не меняя,** если:

- для домена нет блока на 443 или действующий блок без `/admin`/`/miniapp`
  (например, дубль certbot);
- в блоке `return` на уровне server;
- `location /` не `return 404`.

Порт 80, сертификаты, бот, база и приложение не затрагиваются.

## Режимы

- `check` — только диагностика.
- `apply` — повторный запуск безопасен: правка уже есть — только проверки.
- `rollback <каталог копии>` — используйте копию первого успешного `apply`.

## Проверено

Отрепетировано на nginx 1.24 (как в Ubuntu 24.04) с самоподписанным сертификатом для
домена и приложением на `127.0.0.1:3000`:

- конфигурация по инструкции (ссылка);
- копия файла в `sites-enabled` с правкой в `sites-available` — симптом «nginx -t
  проходит, но 404» воспроизведён, диагностика назвала причину, публикация прошла;
- ссылка с оставшимся `location = /`;
- дублирующий блок 443 — безопасная остановка;
- провал проверки — автоматический откат, файл восстановлен побайтно;
- ручной откат и повторный запуск.

Главная, страница решения и `/privacy` в браузере через nginx — без ответов с ошибкой.
На настоящем сервере скрипт не запускался.
