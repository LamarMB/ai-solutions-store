# Мониторинг клиник и уведомления о сбоях

Задача P0-9 (`docs/first-client-roadmap.md`). Один сервис на сервер проверяет каждую
клинику (`docs/clinic-instance-deploy.md`) и сам сервер раз в 5 минут и пишет в Telegram о
проблемах и о восстановлении. Платных сервисов нет.

## 1. Что проверяется

Клиники берутся из `/etc/demo-med/clinics/*.env`. Из этих файлов читаются только
`CLINIC_ID`, `PANEL_PORT` и `PANEL_DOMAIN`. Каждая проверка каждой клиники выполняется
отдельно. Если проверка сама упала (например, база занята), тревога будет только по ней:
«проверка не выполнена». Проблемы других клиник и проверок это не скрывает.

| Проверка          | Тревога                                                                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бот ВКонтакте     | сервис `demo-med-bot@<id>` не работает; нет отметки о связи с ВКонтакте (`last_poll_at` в базе) дольше `MONITOR_BOT_STALE_MINUTES`                                                                                                    |
| Панель            | сервис `demo-med-panel@<id>` не работает; `http://127.0.0.1:<порт>/admin/login` не отвечает или отвечает не 200                                                                                                                       |
| Память сервисов   | бот или панель клиники занимают ≥ `MONITOR_UNIT_MEMORY_MAX_PERCENT` своего лимита `MemoryMax`                                                                                                                                         |
| Резервная копия   | копирование не настроено (`MONITOR_REQUIRE_BACKUP`); копий ещё не было; последняя не создана или не прошла проверку восстановлением (причина из `backup-status.json`, P0-8); последняя успешная старше `MONITOR_BACKUP_MAX_AGE_HOURS` |
| Сертификат https  | для домена клиники nginx не отвечает на 443; сертификат не для этого домена; истекает раньше `MONITOR_CERT_WARN_DAYS` или истёк                                                                                                       |
| Диск сервера      | на разделах `MONITOR_DISK_PATHS` свободно меньше `MONITOR_DISK_MIN_FREE_PERCENT` или `MONITOR_DISK_MIN_FREE_MB` (один раздел — одна тревога)                                                                                          |
| Память сервера    | доступно (`MemAvailable`) меньше `MONITOR_MEMORY_MIN_AVAILABLE_PERCENT`                                                                                                                                                               |
| Настройки клиники | файл настроек не читается или неполный                                                                                                                                                                                                |

Бот и панель проверяются только после включения сервиса (`systemctl is-enabled`). Поэтому
клиника, которую ещё подключают по чек-листу, не тревожит раньше времени. Сертификат
проверяется, только если для клиники включён nginx.

## 2. Уведомления

- **Канал** — Telegram-бот, сообщение в личный чат или группу владельца. Без настроек
  Telegram сообщения пишутся только в журнал (`journalctl -u demo-med-monitor`). В журнал
  они попадают в любом случае.
- **Содержание** — только сервер, клиника, проверка и причина, например
  `• clinic-ivanov — Бот ВКонтакте: нет связи с ВКонтакте 12 мин`. Без данных пациентов,
  текстов разговоров, ключей и токенов. Причина ошибки копии берётся из
  `backup-status.json`, а там её уже очистили от секретов.
- **Защита от спама:**
  - тревога уходит после `MONITOR_FAIL_AFTER` (по умолчанию 2) неудачных проверок подряд:
    перезапуск при обновлении не тревожит;
  - пока проблема не исправлена, повторов нет; напоминание — раз в `MONITOR_REMIND_HOURS`
    (по умолчанию 24 ч);
  - когда проблема исправлена, приходит одно сообщение «✅ Восстановлено» с длительностью
    сбоя;
  - все изменения одной проверки собираются в одно сообщение; длинное обрезается до
    лимита Telegram с отсылкой к журналу;
  - ежедневная сводка в `MONITOR_DAILY_REPORT_HOUR` (по умолчанию 9:00 по времени сервера)
    показывает, что сам мониторинг жив. Если сводки нет, мониторинг не работает.
- **Канал недоступен.** Сообщение не помечается отправленным: повтор при следующей
  проверке, дублей после доставки нет. Сервис завершается с ошибкой, причина — в журнале
  (без токена).

Состояние тревог хранится в `/var/lib/demo-med-monitor/state.json` (700, только root).

## 3. Настройка (один раз на сервер)

Под root из `/opt/demo-med/current`:

1. **Telegram:**
   - создать бота у @BotFather командой `/newbot` и получить токен;
   - написать боту любое сообщение или добавить его в группу;
   - узнать id чата: `curl -s https://api.telegram.org/bot<токен>/getUpdates` →
     `chat.id` (у групп id отрицательный). Токен в чат и в Git не отправлять.
2. **Настройки:**
   ```bash
   install -m 0600 -o root -g root deploy/monitor.env.example /etc/demo-med/monitor.env
   sudoedit /etc/demo-med/monitor.env     # MONITOR_TELEGRAM_BOT_TOKEN, MONITOR_TELEGRAM_CHAT_ID, пороги
   ```
3. **Сервис и таймер:**
   ```bash
   install -m 0644 deploy/systemd/demo-med-monitor.service deploy/systemd/demo-med-monitor.timer /etc/systemd/system/
   systemctl daemon-reload
   set -a; . /etc/demo-med/monitor.env; set +a
   node node_modules/tsx/dist/cli.mjs scripts/monitor.mts check   # настройки
   node node_modules/tsx/dist/cli.mjs scripts/monitor.mts test    # тестовое сообщение в Telegram
   systemctl enable --now demo-med-monitor.timer
   systemctl start demo-med-monitor.service && journalctl -u demo-med-monitor -n 20 --no-pager
   ```
4. **Проверка тревоги.** Остановить панель тестовой клиники
   (`systemctl stop demo-med-panel@<id>`). Через 5–10 минут придёт тревога. Запустить
   панель — придёт «Восстановлено».

Пороги меняются в `/etc/demo-med/monitor.env` без изменения кода; действуют со
следующей проверки.

## 4. Права сервиса

Сервис работает от root, но из прав у него остаётся только `CAP_DAC_READ_SEARCH`: чтение
настроек и баз клиник (600/700) без права записи. Файловая система — только для чтения
(`ProtectSystem=strict`). Писать сервис может только в своё состояние
(`StateDirectory=demo-med-monitor`). База клиники открывается только на чтение; SQLite
читает работающую базу в режиме WAL с раздела «только чтение» (проверено).

## 5. Ограничения

- Мониторинг стоит на том же сервере. Если сервер выключен целиком, сообщений не будет:
  об этом говорит только отсутствие ежедневной сводки. Внешняя проверка доступности
  (например, бесплатный тариф внешнего сервиса) — по решению владельца.
- Telegram должен быть доступен с сервера. Если `api.telegram.org` не отвечает,
  сообщения копятся в журнале и уходят при восстановлении связи. Можно указать свой
  адрес Bot API (`MONITOR_TELEGRAM_API`).
- Проверки бота смотрят на связь с ВКонтакте, но не на качество ответов пациентам.
