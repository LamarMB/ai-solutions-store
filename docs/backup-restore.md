# Резервные копии клиник и восстановление

Задача P0-8 (`docs/first-client-roadmap.md`). Для каждого экземпляра клиники
(`docs/clinic-instance-deploy.md`): ежедневная зашифрованная копия базы SQLite во
внешнем хранилище с проверкой восстановлением.

## 1. Как устроено

Сервис `demo-med-backup@<id>` (запускает таймер `demo-med-backup@<id>.timer` каждую ночь в
03:00 + до 90 минут случайной задержки; пропущенный запуск выполняется после включения
сервера):

1. **Снимок** работающей базы — `VACUUM INTO` в одной транзакции чтения: согласованная
   копия со всем подтверждённым, в том числе из журнала WAL; бот и панель продолжают
   работать; `PRAGMA integrity_check`.
2. **Шифрование** — AES-256-GCM, перед этим gzip. Ключ — `BACKUP_KEY` клиники (отдельный от
   `MEDICAL_DATA_KEY`), через HKDF с идентификатором клиники: копию одной клиники нельзя
   расшифровать ключом другой и восстановить в другую. Заголовок копии (клиника, время,
   версия схемы, размер, SHA-256) защищён тегом GCM. Незашифрованный снимок удаляется сразу.
3. **Локальная копия** (зашифрованная) — `/var/backups/demo-med/<id>`, последние
   `BACKUP_LOCAL_KEEP`. Это быстрый откат, **не резервирование**.
4. **Внешнее хранилище** — `BACKUP_TARGET`:
   - `s3://<бакет>/<каталог>` — любое S3-совместимое хранилище (подпись AWS Signature V4,
     адреса `<endpoint>/<бакет>/<ключ>`); копии клиники — в `<каталог>/<id>/`;
   - `file:///<путь>` — смонтированный внешний диск или сетевое хранилище, копии — в
     `<путь>/<id>/`. Каталог на том же диске, что база, проверка помечает предупреждением.
5. **Проверка восстановлением** — копия скачивается из хранилища, сверяется с
   отправленной, расшифровывается, база проверяется `integrity_check` и сверяется со
   снимком (версия схемы, число записей).
6. **Срок хранения** — только после успешной проверки новой копии: во внешнем хранилище
   остаются `BACKUP_KEEP` новых копий этой клиники (чужие и посторонние файлы не
   трогаются). Если список хранилища недоступен, старые копии не удаляются (предупреждение).
   `BACKUP_KEEP=0` — копии не удаляются, срок задаёт правило жизненного цикла хранилища.

Сбой на любом шаге — сервис завершается с ошибкой, старые копии не удаляются, временные
файлы (снимок, расшифровка, `.partial`) удаляются; остатки прерванного запуска убирает
следующий. Одновременно — один запуск на клинику. Состояние последнего запуска —
`/var/lib/demo-med/<id>/backup-status.json` (без секретов) — для мониторинга (P0-9).

**Журнал** — `journalctl -u demo-med-backup@<id>`: шаги, размер, версия схемы, число
записей, имя копии, причина ошибки (например, `отправка: хранилище (S3 …): PUT — HTTP 403
AccessDenied — доступ запрещён — проверьте ключи и права на бакет`). Ключей, адресов с
подписью, тела ответов хранилища и содержимого базы в журнале нет.

## 2. Изоляция клиник

- Свои `BACKUP_KEY` (проверка запрещает совпадение у двух клиник и с `MEDICAL_DATA_KEY`),
  свой каталог в хранилище, удаление только своих копий.
- Сервис копирования работает от пользователя клиники `dm-<id>`, пишет только в
  `/var/lib/demo-med/<id>` и `/var/backups/demo-med/<id>` (оба `700`).
- Настройки копий — отдельный файл `/etc/demo-med/backup/<id>.env` (`600 root`): ключ копий и
  доступ к хранилищу получает только сервис копирования; бот и панель (доступная из
  интернета) их не получают, а сервис копирования не получает секретов бота.
- В S3 лучше отдельный сервисный аккаунт (ключ) на клинику с доступом только к её каталогу
  — так одна клиника не сможет прочитать или удалить копии другой даже при утечке ключа.
  Настраивается у провайдера (политика доступа к префиксу).

## 3. Настройка для клиники

Под root из `/opt/demo-med/current`. Шаблоны сервиса и таймера ставятся один раз вместе
с остальными:

```bash
install -m 0644 deploy/systemd/demo-med-backup@.service deploy/systemd/demo-med-backup@.timer /etc/systemd/system/
systemctl daemon-reload
```

1. `deploy/clinic/new-clinic.sh backup-init <id>` — файл `/etc/demo-med/backup/<id>.env` с
   новым `BACKUP_KEY` (ключ не выводится).
2. **Сохраните `BACKUP_KEY` и `MEDICAL_DATA_KEY` вне сервера** (менеджер паролей
   владельца): `sudo cat /etc/demo-med/backup/<id>.env` и
   `sudo cat /etc/demo-med/clinics/<id>.env` — только на своём экране, не в чат. Без
   `BACKUP_KEY` копии не расшифровать; без `MEDICAL_DATA_KEY` в восстановленной базе не
   прочитать разговоры и согласия.
3. `sudoedit /etc/demo-med/backup/<id>.env`: `BACKUP_TARGET` и для S3 — `BACKUP_S3_ENDPOINT`,
   `BACKUP_S3_REGION`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY`.
   Для `file://` дополнительно разрешить сервису запись в этот каталог:
   `systemctl edit demo-med-backup@<id>.service` →
   `[Service]` / `ReadWritePaths=<путь>/<id>`.
4. `new-clinic.sh backup-check <id>` — проверка настроек.
5. `new-clinic.sh backup <id>` — первая копия сейчас (тот же сервис, что у таймера), журнал
   выводится. Затем `new-clinic.sh backup-verify <id>` — проверка восстановлением.
6. `new-clinic.sh backup-enable <id>` — включить ежедневный таймер.

Проверять восстановление вручную — раз в месяц (`backup-verify`) и после смены хранилища.

## 4. Восстановление

Рабочая база никогда не перезаписывается автоматически.

1. Список копий: `new-clinic.sh backups <id>` (новые первыми).
2. Расшифровка в **новый** файл в каталоге клиники с проверкой (клиника, ключ, контрольная
   сумма, `integrity_check`):
   ```bash
   new-clinic.sh restore <id> demo-med-<id>-<ГГГГММДД>T<ЧЧММСС>Z.dmbk
   # → /var/lib/demo-med/<id>/restore-<время>.sqlite, сводка: схема, записей
   ```
   Восстановление поверх рабочей базы, её `-wal`/`-shm` или существующего файла программа
   отклоняет.
3. Замена рабочей базы — только с подтверждением идентификатором клиники:
   ```bash
   new-clinic.sh restore-apply <id> /var/lib/demo-med/<id>/restore-<время>.sqlite --confirm=<id>
   ```
   Останавливает бота, панель и таймер копий; прежние `bot.sqlite`, `-wal`, `-shm`
   **переименовываются** в `*.before-restore-<время>` (не удаляются); ставит восстановленную
   базу; запускает сервисы. Записи, сделанные после копии, в восстановленной базе
   отсутствуют — сообщите клинике.
4. Проверка: панель (записи, врачи, настройки), бот (`new-clinic.sh status <id>`).

**Новый сервер** (прежний недоступен): развернуть экземпляр (`docs/clinic-instance-deploy.md`,
шаги 1–3) с прежними `MEDICAL_DATA_KEY` и `BACKUP_KEY` из хранилища владельца, настроить
то же хранилище, затем шаги 1–4 выше. Без доступа к хранилищу — копия из локального
каталога или скачанная вручную:
`… scripts/clinic-backup.mts restore --file=<копия.dmbk> --out=<новый файл>`.

## 5. Внешнее хранилище: что нужно от владельца

Провайдер не выбран. Подходит любое S3-совместимое хранилище **в другой площадке, чем
VPS** (для размещения данных в РФ — российский провайдер, решение с юристом):

- бакет (приватный), регион и адрес API (`https://…`);
- сервисный аккаунт и статический ключ доступа (ID и секрет) с правами: запись, чтение,
  список и удаление — только в этом бакете (лучше — только в каталоге клиники);
- желательно: версионирование или блокировка объектов (защита от удаления копий при
  взломе сервера) и правило жизненного цикла; тогда `BACKUP_KEEP=0`.

Объём: копия сжата, для клиники — единицы мегабайт; 30 копий — десятки мегабайт.
Платные сервисы без согласования не подключаются.

## 6. Ограничения

- Копия ежедневная: при потере сервера теряются изменения с последней копии (до суток).
- Уведомлений о неудачной копии пока нет — смотреть `systemctl list-timers` и журнал;
  оповещения — задача P0-9 (`backup-status.json`).
- Копия целиком в памяти процесса (`MemoryMax=1G`) — достаточно для баз клиник в десятки
  мегабайт.
- На настоящем сервере и с настоящим хранилищем не проверялось; подпись S3 проверена на
  примерах из документации AWS и тестовом сервере.
