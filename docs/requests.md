# Заявки: архитектура и запуск

## Текущее состояние — тестовый режим

Приём заявок **не запущен**. Форма `/request` работает полностью, но сервер использует
тестовый адаптер `TestRequestStore`: данные проверяются и **отбрасываются** — не сохраняются
в файлы, базу или память процесса и никуда не передаются. Сохраняется только счётчик
принятых проверок. Пользователь видит это на странице (плашка «Приём заявок ещё не
запущен», кнопка «Отправить (тестовый режим)», сообщение «Проверка пройдена — заявка не
отправлена»). Страница `/privacy` — честная заглушка без реквизитов.

## Заявка на демонстрацию с главной (доставка в Telegram)

Короткая форма в разделе `#demo`: имя, клиника, способ связи (Telegram, телефон или
email) и согласие. Тот же обработчик, что у `/request`: повтор, частота, ловушка, время
заполнения, проверка схемы (`DemoRequestSchema`, поле `form=demo`).

**Включение.** Форма появляется, а заявки доставляются, только если выполнены оба
условия; иначе на сайте остаётся кнопка Telegram, форма не показывается:

1. **Политика опубликована.** В `src/content/privacy.ts` задан `privacyPolicy`:
   оператор, контакт, дата и текст, утверждённые юристом. Страница `/privacy`
   покажет его вместо заглушки. В тексте указать, что заявки передаются оператору
   через мессенджер Telegram.
2. **Доставка настроена.** В `.env.local` на сервере заданы
   `REQUESTS_TELEGRAM_BOT_TOKEN` (бот от @BotFather) и `REQUESTS_TELEGRAM_CHAT_ID`
   (чат владельца; сначала написать боту `/start`, иначе он не сможет отправлять сообщения).

После этого — пересборка и перезапуск: главная собирается статически, режим формы
определяется при сборке.

**Как работает.** Заявка не хранится на сервере. Она уходит одним сообщением в
Telegram (`sendMessage`, без разметки) с номером, полями и отметкой о согласии.

- «Заявка отправлена» пользователь видит только после ответа Telegram `ok: true`.
- Ошибка доставки — сообщение об ошибке и ссылка на Telegram, введённое сохраняется.
- В журнал пишутся только номер заявки и режим. Имя, контакт и токен туда не попадают
  (тесты `src/requests/demo-request.test.ts`).

**Ограничение.** Telegram — внешний сервис, сервер которого может находиться вне РФ.
Допустимость такой передачи контактных данных и текст согласия согласуйте с юристом
до включения.

## Как устроено

| Часть                                                                 | Файл                                     |
| --------------------------------------------------------------------- | ---------------------------------------- |
| Схема полей (Zod), общая для клиента и сервера                        | `src/requests/schema.ts`                 |
| Обработка: повтор → частота → антиспам → схема → каталог → сохранение | `src/requests/service.ts`                |
| Состояние формы для интерфейса                                        | `src/requests/state.ts`                  |
| Хранилище: интерфейс `RequestStore` и `TestRequestStore`              | `src/requests/store.ts`                  |
| Ограничение частоты и защита от повторной отправки                    | `src/requests/rate-limit.ts`             |
| Server Action                                                         | `src/app/(site)/request/actions.ts`      |
| Форма                                                                 | `src/components/request/RequestForm.tsx` |

- **Данные заявки (минимум):** имя, компания (необязательно), способ связи и контакт,
  описание задачи, позиции «решение + пакет» (черновик заказа; пусто — общая заявка).
  IP-адрес, user-agent и служебные поля не сохраняются.
- **Решение и пакет** берутся из URL и проверяются по каталогу на сервере; неизвестное
  отбрасывается.
- **Проверка:** одна Zod-схема на клиенте (до отправки) и на сервере (обязательно).
- **Повторная отправка:** кнопка блокируется на время отправки; у каждой формы ключ
  `submissionId` — повтор с тем же ключом возвращает прежний результат без новой заявки.
- **Спам:** скрытое поле-ловушка (бот получает обычный ответ, ничего не сохраняется) и
  минимальное время заполнения 3 секунды.
- **Частота:** 8 попыток за 10 минут на клиента. Ключ — SHA-256 от IP с солью, которая
  живёт только в памяти процесса; сам IP не хранится. IP — последний адрес
  `X-Forwarded-For` (первые может подставить клиент).
- **Логи:** только `id`, режим и число позиций. Имя, контакты и текст в лог не пишутся
  (проверяется тестами).
- **Встроено в Next.js:** проверка `Origin` для Server Actions (CSRF) и лимит тела 1 МБ.

## Что нужно для запуска реального приёма

Включать только после выполнения **всех** пунктов:

1. **Юридическое:** утверждённая политика обработки персональных данных и сведения об
   операторе; текст согласия, согласованный с юристом; при необходимости — уведомление
   регулятора и соблюдение требований к локализации данных (152-ФЗ).
2. **Хранилище:** выбранная и настроенная база или сервис с шифрованием, доступом по
   ролям, резервным копированием и сроком хранения/удаления заявок. Реализовать адаптер
   `RequestStore` (например, `DatabaseRequestStore`) и выбор в `getRequestStore()` по
   переменной окружения; секреты — только в окружении, не в репозитории.
3. **Масштабирование:** при нескольких инстансах перенести ограничение частоты и кэш
   повторных отправок из памяти процесса в общее хранилище.
4. **Прокси:** ключ клиента строится из последнего адреса `X-Forwarded-For`
   (`src/lib/client-key.ts`). Reverse proxy должен перезаписывать заголовок адресом
   клиента (`proxy_set_header X-Forwarded-For $remote_addr`), а Node.js — слушать только
   `127.0.0.1` (см. `deployment-plan.md`); при необходимости — `serverActions.allowedOrigins`.
5. **Уведомления** о новых заявках (почта, CRM) — отдельным решением; сейчас не подключены.
6. **Интерфейс:** заменить `/privacy` на утверждённый текст; режим `"test"` сменится
   автоматически вместе с хранилищем — плашка и подписи тестового режима исчезнут.
