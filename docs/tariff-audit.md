## 0. Главный вывод

**Сейчас продукт нельзя подключить к реальной клинике без доработки.** Это не мелкие
недочёты, а режим работы:

1. **Бот и Mini App отвечают только тестовым аккаунтам.** `VK_ALLOWED_USER_IDS`
   обязателен (`src/bot/config.ts`), посторонний получает «Это демонстрационный бот
   тестовой клиники» (`src/bot/vk/runner.ts`); у Mini App пустой список — доступа нет ни
   у кого. Режима «все пациенты» нет.
2. **Пометки демо зашиты в код:** приветствие «(демо, данные вымышленные)», «Запись
   подтверждена (тестовое расписание)», инструкция OpenAI «демонстрационной вымышленной
   клиники», бренд «Демо-Мед» и плашки «Демо» в Mini App, «(демонстрационный бот)» в
   уведомлении администратору.
3. **Публичный сайт не опубликован:** nginx отдаёт наружу только панель и Mini App
   (`docs/admin-panel-deploy.md`, раздел 9); кнопка Telegram на сайте клиентам недоступна.
4. **Интеграции с МИС нет**, а интерфейс расписания синхронный — подключение внешней МИС
   требует переделки (раздел 3).
5. **Правовая база не готова:** политика конфиденциальности — заглушка; согласия на
   обработку и передачу данных в OpenAI, договор поручения с клиникой, размещение данных
   в РФ — не подтверждены (раздел 4).

Что готово и работает — сильная сторона: запись без двойных бронирований, панель с
ролями и журналами, обращения с согласием, правила безопасности до ИИ, параллельная
обработка бота (в ветке). Всё проверено тестами (729) и локальной нагрузкой.

**Состояние на сервере:** развёрнут `main` (`47323c6`). Владелец подтвердил запись в
боте и Mini App на телефоне с тестовым аккаунтом. Не развёрнуты: исправления аудита
демонстрации, предупреждение о переписке, параллельная обработка бота, изменения сайта.
Работа с OpenAI на сервере в документах не подтверждена (неизвестно, задан ли ключ).

## 3. Интеграция с МИС

### 3.1. Что есть сейчас

- **Реальных интеграций с МИС нет ни одной.** Упоминания — только в документации и
  на сайте («оценивается отдельно»).
- Есть интерфейс `ScheduleProvider` (`src/bot/schedule/schedule.ts`) с комментарием
  «позже — интеграция с МИС», но:
  - он **синхронный** (`book()` сразу возвращает результат) — внешний API асинхронный;
  - его использует только бот; **Mini App и панель работают с `ClinicSchedule` и
    таблицами SQLite напрямую** (`src/miniapp/service.ts`, `src/admin/service.ts`);
  - перенос (`reschedule`), поиск записей, отметка «состоялся» в интерфейс не входят.

### 3.2. Что зависит от собственной SQLite

| Данные                               | Где                                                   | При интеграции с МИС                                                         |
| ------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------- |
| Врачи, направления, услуги и цены    | `clinic-store.ts`, панель «Врачи», «Настройки»        | Источник — МИС (синхронизация), в панели — только наши поля (фото, описание) |
| Часы приёма, выходные, перерывы      | `doctor_hours`, `schedule_exceptions`                 | Источник — МИС; редактирование в панели отключить                            |
| Записи пациентов                     | `bookings` (уникальный индекс слота)                  | Источник — МИС; у нас — связь «VK ID ↔ запись МИС» и статус                  |
| Разговоры, согласия врачу, обращения | `sessions`, `disclosure_consents`, `patient_requests` | Остаются у нас; согласия привязаны к номеру записи — перейти на внешний id   |
| Сотрудники, роли, журналы            | `admin_*`, `*_access_log`                             | Остаются у нас                                                               |

### 3.3. Что потребуется для подключения МИС через API

1. **Асинхронный провайдер расписания** для бота, Mini App и панели: список врачей,
   свободные слоты, запись, отмена, перенос, записи пациента — через один интерфейс;
   текущая логика — реализация «расписание в панели».
2. **Адаптер МИС:** авторизация, сопоставление врачей/услуг/филиалов, ошибки и лимиты,
   журнал без персональных данных.
3. **Идентификация пациента в МИС:** МИС обычно требует ФИО, телефон, дату рождения —
   сейчас бот и Mini App их **не собирают** (принцип минимизации). Сбор и передача этих
   данных в МИС — новая обработка персональных данных: решение владельца и юриста.
4. **Синхронизация:** кэш врачей и слотов на секунды-минуты; записи, созданные и
   отменённые в самой МИС, — через вебхуки или опрос.
5. **Панель:** расписание — только просмотр, без второго ведения.

### 3.4. Как исключить двойные записи с внешней МИС

- **Решение о записи принимает МИС**, а не наш кэш: свободный слот из кэша — только
  подсказка; ответ МИС «занято» → пациенту «время заняли, вот другое».
- **Ключ идемпотентности на действие пациента:** перед вызовом МИС сохраняем
  «ожидающую запись» с ключом; при тайм-ауте не повторяем вслепую, а спрашиваем МИС по
  ключу/слоту и сверяем — иначе возможна двойная запись после повтора.
- **Порядок по пациенту** уже есть (`KeyedQueue` в `claude/bot-concurrency`): один
  пациент не создаст две записи параллельно.
- Если МИС поддерживает **временную бронь слота** — использовать её на шаге
  подтверждения.
- Регулярная **сверка** наших записей с МИС (отменённые в МИС — отмечать у нас).

### 3.5. Что переиспользуется

Диалог записи и подтверждения, Mini App (экраны, подпись запуска), очередь бота,
согласия и обращения, роли панели, типы результатов `taken` / `unavailable` / `limit`,
правила безопасности, тесты сценариев (их можно прогонять против заглушки МИС).

### 3.7. «Инфоклиника», MEDODS, МедФлекс — что известно

Публичной технической документации API ни одной из трёх поиск не нашёл. Совместимость
**не подтверждена**:

- **«Инфоклиника» («Инфодент»)** — есть коммерческие интеграции через Битрикс24
  (онлайн-запись, расписание, перенос/отмена), значит у системы есть механизм обмена;
  его вид, условия и цена — у разработчика или его партнёров.
- **MEDODS** — позиционируется как МИС «с открытым API»; сторонний сервис (Callibri)
  подключается по домену CRM и пользователю «Права доступа к API». Методы записи и
  условия — запросить у MEDODS.
- **МедФлекс (ООО «МедРокет»)** — в найденном договоре API описан как часть системы с
  доступом по токену, в контексте передачи данных (в т. ч. в ЕГИСЗ); подходит ли он как
  шина для онлайн-записи из внешнего приложения — не подтверждено.

Источники: [приложение «Онлайн-запись в МИС Инфоклиника» в Битрикс24](https://www.bitrix24.ru/apps/app/rs24.integratsiya_mis_infoklinika_i_bitriks24_s_onlayn_zapisyu/),

| Врачебная тайна (ст. 13 323-ФЗ)             | Факт записи к врачу хранится у нас и во ВКонтакте; руководители сообщества видят переписку                                    | Факт обращения за помощью — врачебная тайна; видимость переписки во ВКонтакте не устранена (`decisions.md`, Р-09)                                                     |
| Передача текста в OpenAI (трансграничная)   | Текст без телефонов и почты; `store: false`                                                                                   | Передача ПДн за рубеж; имена и симптомы могут остаться в тексте; требования к трансграничной передаче и уведомлению — к юристу; вариант — работа без OpenAI (правила) |
| Размещение данных в РФ (ст. 18 ч. 5 152-ФЗ) | Расположение VPS в репозитории не указано; перед Mini App — «российский прокси»                                               | Если основной сервер за пределами РФ — нарушение требования локализации для реальных пациентов. **Подтвердить расположение**                                          |
| Права доступа                               | Роли `owner`/`admin`/`doctor`, журналы доступа, шифрование согласий, сессии HttpOnly                                          | Нет второго фактора; ключ шифрования на том же сервере; low-замечания ревью (приглашения, блокировка входа) открыты                                                   |
| Хранение и удаление                         | Сроки: разговор 24 ч, обращения 30/7 дней, согласия — по сроку                                                                | Нет процедуры по запросу пациента на удаление/ознакомление; резервные копии — вручную и на том же сервере                                                             |
