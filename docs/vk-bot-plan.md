# План: VK-бот ИИ-администратора клиники (прототип)

Статус: **этап Б1 выполнен** (ядро, тестовое расписание, SQLite, симулятор, тесты).
ВКонтакте и LLM не подключены.

Цель прототипа — показать клинике работу ИИ-администратора в сообщениях сообщества
ВКонтакте: ответы на организационные вопросы, выбор врача и свободного времени,
подтверждение записи по **тестовому расписанию с вымышленными врачами**, передача
диалога администратору. Реальных пациентов, медицинских данных и интеграции с МИС нет.

## Этап Б1: что сделано и как проверить

```
src/bot/
  clinic/      вымышленная клиника «Демо-Мед»: направления, врачи, часы приёма
  schedule/    ScheduleProvider и ClinicSchedule: свободные дни и слоты, запись, отмена
  storage/     BookingRepository и SessionStore; SqliteStore на встроенном node:sqlite
  dialog/      состояние и кнопки диалога, правила разбора текста (RuleInterpreter)
  bot.ts       createBot: загрузка/сохранение сессии + шаг диалога, без привязки к каналу
  index.ts     createDemoBot — сборка вымышленной клиники с базой SQLite
scripts/bot-sim.mts   симулятор диалога в терминале
```

- **Хранение:** SQLite-файл `.data/bot.sqlite` (в `.gitignore`). Записи и шаг диалога
  переживают перезапуск. Текст сообщений не сохраняется — только шаг сценария.
- **Двойное бронирование:** уникальный индекс SQLite по активному слоту врача
  (`doctor_id, date, time WHERE cancelled_at IS NULL`) плюс проверка в сервисе; второй
  пациент получает «время только что заняли» и новый список. Подтверждение и отмена
  берутся из сохранённого состояния, поэтому старые и подделанные кнопки ничего не
  бронируют и не отменяют.
- **Правила записи:** только часы приёма врача, не раньше чем за час, на две недели вперёд,
  не больше трёх активных записей у собеседника, отменить можно только свою запись.
- **Независимость от канала и LLM:** `createBot(...).handle(peerId, event)` принимает
  событие (`start`, текст, нажатие кнопки) и возвращает ответы (текст и ряды кнопок).
  ВКонтакте (Б2) станет транспортом; LLM — реализацией `TextInterpreter`;
  МИС — реализацией `ScheduleProvider`.

**Локальная проверка (Node.js 24):**

```bash
npm ci
npm run bot:sim                 # собеседник 1
npm run bot:sim -- --peer=2     # второй собеседник — проверка занятого времени
```

Номер — нажать кнопку, текст — написать боту (например, «записаться», «мои записи»),
`выход` — завершить. Сбросить тестовые записи — удалить папку `.data`.
Автотесты бота: `npx vitest run src/bot`.

## 1. Границы прототипа

- Только сообщения сообщества ВКонтакте; чат на сайте и другие каналы — позже.
- Расписание — собственное тестовое: вымышленная клиника, врачи и слоты. Записи хранятся
  в локальной базе SQLite и сохраняются после перезапуска.
- Подтверждение записи — по тестовому расписанию. В интерфейсе бота это явно сказано.
- Бот отвечает только пользователям из списка тестовых аккаунтов (`VK_ALLOWED_USER_IDS`);
  остальным — короткое сообщение, что это демонстрационный прототип.
- Бот не собирает ФИО, телефоны, жалобы и документы. Хранится только `peer_id` ВКонтакте
  и вымышленная запись. Шаги «подготовка к приёму» и «сводка врачу» из сценария на сайте
  в прототип не входят.
- ИИ не ставит диагнозы и не даёт медицинских советов — используется тот же запрет, что и в
  консультанте сайта (`MEDICAL_ADVICE_STEMS`).

## 2. Архитектура

Бот живёт в том же репозитории, отдельно от страниц сайта, и не меняет работу сайта.

```
src/bot/
  core/        чистая логика диалога: состояние → событие → новое состояние + ответы
  schedule/    ScheduleProvider (интерфейс) и TestScheduleProvider (вымышленные данные)
  answers/     ответы на вопросы: правила сейчас, LLM позже (через ChatProvider-подход)
  vk/          клиент VK API (fetch), клавиатуры, Long Poll, разбор событий
scripts/vk-bot.ts   запуск: чтение переменных окружения и цикл Long Poll
```

- **Ядро без ВКонтакте.** `handleEvent(state, event)` возвращает новое состояние и список
  ответов (текст + кнопки). Так весь сценарий записи проверяется unit-тестами и локальным
  симулятором в терминале (`npm run bot:sim`) без токена и сети.
- **`ScheduleProvider`**: `listSpecialties`, `listDoctors(specialty)`, `listDays(doctor)`,
  `listSlots(doctor, day)`, `book(slot, peerId)`, `cancel(bookingId)`. Сначала
  `TestScheduleProvider`; позже `MisScheduleProvider` — после отдельной оценки МИС клиники.
  Повторная запись на занятый слот отклоняется (защита от гонки двух пользователей).
- **Транспорт — Bots Long Poll** для прототипа: бот сам обращается к серверам ВКонтакте,
  публичный адрес, домен и https не нужны. Callback API (адрес на сервере сайта,
  строка подтверждения, секретный ключ) — на этапе production вместе с развёртыванием
  (`deployment-plan.md`).
- **VK API**: `messages.send` с обязательным `random_id` (защита от повторной отправки),
  кнопки — callback-кнопки (событие `message_event` + `messages.sendMessageEventAnswer`),
  версия API — актуальная на момент разработки (сверить на dev.vk.com). Обработка ошибок
  Long Poll (`failed`: обновить `ts` или запросить новый сервер), повторов и лимитов частоты.
- **ИИ-ответы.** Свободный текст сначала разбирается правилами (запись, отмена, вопрос,
  администратор). Ответы на вопросы — по базе знаний вымышленной клиники. Подключение LLM
  (YandexGPT или GigaChat, см. `production-readiness.md` §6) — отдельным решением; LLM
  выбирает намерение и отвечает только по базе знаний, а врачей и слоты бот берёт из
  `ScheduleProvider`, никогда из текста модели.
- **Запуск.** Скрипт на Node.js 24 вне Next.js через dev-зависимость `tsx` (импорты `@/*`
  без сборки). Скрипты — `.mts` (ES-модули).

## 3. Сценарий диалога

1. **Начать** → приветствие и пометка: «Демонстрационный прототип. Врачи и расписание
   вымышленные. Не отправляйте медицинские данные». Кнопки: «Записаться», «Задать вопрос»,
   «Мои записи», «Администратор».
2. **Записаться** → направление (терапевт, стоматолог, …) → врач → день (ближайшие дни со
   свободными слотами) → время → сводка «Врач, дата, время. Подтвердить?» →
   **Подтвердить** → «Вы записаны (тестовое расписание)». На каждом шаге — «Назад» и
   «Отмена»; если пока пользователь выбирал, слот заняли, — предложить другие.
3. **Мои записи** → список с кнопкой «Отменить запись».
4. **Задать вопрос** → ответ по базе знаний (услуги, цены, адрес, график, подготовка к
   визиту); медицинский вопрос — вежливый отказ и совет обратиться к врачу.
5. **Администратор** → уведомление администратору в личные сообщения ВКонтакте
   (номер диалога, без медицинских подробностей) и пауза бота в этом диалоге, пока
   администратор отвечает вручную (по событию исходящего сообщения от сотрудника).

После подтверждения записи бот ничего больше не требует — пациент может закрыть диалог.

## 5. Настройки сообщества ВКонтакте (делает владелец)

Названия пунктов меню могут отличаться — сверяйтесь с интерфейсом ВКонтакте.

1. **Управление → Сообщения:** включить сообщения сообщества.
2. **Сообщения → Настройки для бота:** включить «Возможности ботов» и кнопку «Начать»;
   добавление в беседы — не нужно.
3. **Работа с API → Ключи доступа:** создать ключ с правом **«Сообщения сообщества»**
   (других прав не нужно). Ключ создаёт администратор: если он потеряет права, ключ
   перестанет работать.
4. **Работа с API → Long Poll API:** включить, выбрать последнюю версию API, отметить
   события: входящее сообщение, исходящее сообщение, действие с сообщением (нажатие
   callback-кнопки), разрешение и запрет на получение сообщений.
5. Пока идёт прототип — не продвигать сообщество; бот всё равно отвечает только тестовым
   аккаунтам.

## 7. Риски и ограничения

- Переписка в ВКонтакте — персональные данные (ID пользователя, текст). Прототип работает
  только с тестовыми аккаунтами; для реальных пациентов нужны политика ПДн, согласие и
  инфраструктура из `production-readiness.md`.
- Bots Long Poll работает, пока запущен процесс: для показа клинике процесс должен быть
  постоянно включён (компьютер или сервер).
- Лимиты VK API на отправку сообщений и размеры клавиатуры уточнить по документации
  dev.vk.com при разработке (в сторонних источниках данные расходятся).
